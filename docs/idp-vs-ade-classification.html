Grounded DocParse · Classification brief

Is this repository IDP or ADE?

A grounded classification of grounded-docparse based on repository design docs, workflow contracts, and source modules — not marketing labels.

Verdict: primarily ADE (Agentic Document Extraction pattern)

Primary: ADE / agentic document intelligence Partial IDP capabilities Foundation: local OCR owns evidence Not classic enterprise IDP platform

This repo implements a bounded, evidence-grounded agentic document system: local visual parse first, then optional specialized reasoning tasks (classify, section, route, extract, chat), with deterministic validation, finite repair, grounding to local OCR identity/geometry, and human review gates.

It is not a full enterprise IDP product (no RPA connectors, no multi-user BPM, no queue/workers, no durable job store, no systems-of-record write-back). It does, however, deliver several IDP-like outcomes (schema extraction, form routing, review, reusable profiles) inside an ADE-style architecture.

Package description in pyproject.toml: “Grounded agentic document parser for structured Markdown and JSON.”

1. Definitions used here

OCR

Image/page → text regions, often with boxes and confidence. No business workflow by itself.

IDP (Intelligent Document Processing)

Enterprise category: classify + extract + validate + human-in-the-loop + route into business systems. Often template/ML pipelines plus workflow integration.

ADE (Agentic Document Extraction)

Modern document-intelligence pattern: visual/structural parse → grounded intermediate representation (Markdown/JSON/elements) → goal-directed tasks (classify, split/section, extract, answer) with validation, uncertainty, and source grounding. LandingAI brands a managed product “ADE”; this repo implements a related pattern, not that product.

Important distinction

ADE is an architecture/pattern. IDP is often a product category. A system can be ADE-shaped while only partially covering IDP outcomes — that is this repository.

3. End-to-end workflow

From docs/architecture.md, docs/how-it-works.md, and README.md.

Browser
  → Streamlit (`streamlit_app.py`)
     → ingest + rasterization (no selectable PDF text)
     → selected local OCR
        → GLM-OCR / vLLM (or Ollama)  OR  PaddleOCR-VL-1.6 / PaddleX
     → deterministic quality / recovery planning
     → optional Luna crop recovery (text-only on existing regions)
     → grounded Markdown + hierarchy + JSON + annotated PDF
     → optional Luna document features:
          refine | classify | TOC | form routing | extract | chat
     → downloads + source highlighting

Ordered stages

1
Validate & ingest — extension, bytes, page/pixel limits; rasterize every page to PNG.
2
Local OCR perception — layout + recognition. This stage owns text, type, order, IDs, boxes, confidence.
3
Deterministic quality — rank weak regions (low confidence, empty large regions, density/garbage, weak tables).
4
Optional visual recovery — engine-local form recovery + optional Luna crops; only high-confidence text replacements (≥ 0.85) accepted.
5
Materialize parse — hierarchy, base Markdown, refined Markdown (optional), parse JSON v4.4, annotated PDF.
6
Optional agentic analysis — classification + TOC concurrently; failures isolated; TOC can fall back to grounded headings.
7
On-demand extraction / routing / chat — user-triggered; schema/profile driven; citations must resolve to known evidence.
Parsing remains useful without Luna or an API key. Agentic stages are optional enhancements around a completed local parse.

4. Design principles (why this is ADE-shaped)

  1. Parse-then-reason split. Local OCR establishes the evidence geometry first; models reason later over crops or compact structured context (docs/research.md).
  2. Evidence ownership is a control plane. Local OCR owns element ID, normalized box, type, structure, reading order, and OCR confidence. Luna recovery may change only existing-region text when crop confidence ≥ 0.85. Additions, deletions, geometry, type, and order changes are ignored (docs/architecture.md ownership table).
  3. Specialized roles, not one free-form prompt. Roles include visual recovery, Markdown refinement, classification, TOC, form routing, extraction, chat (docs/how-grounded-docparse-is-agentic.md).
  4. Deterministic validation after model proposals. Categories must exist; segments must cover pages; extraction citations must map to active blocks/atoms; cited source text must support the value; chat citations must be known element IDs.
  5. Finite repair loops. One schema-repair attempt for structured features; extraction may do one evidence-repair call; then stop, warn, fall back, or return null/not_found — no infinite “prompt until it looks good.”
  6. Human control and uncertainty. Low-confidence / boundary-merged routing needs review. Extraction does not auto-run after parse. Chat is off until enabled. Unresolved leaves stay explicit rather than invented.
  7. Bounded autonomy only. No self-invented goals, arbitrary tools, durable agent memory, or acting on external business systems.

5. Technical architecture details

System boundary

  • UI / orchestration: one synchronous Streamlit process (streamlit_app.py).
  • Local OCR backends (exclusive GPU selection in launchers): GLM-OCR via SDK → vLLM/Ollama, or PaddleOCR-VL-1.6 via PaddleX API → local vLLM.
  • Optional cloud reasoning: OpenAI Responses API through gateways.py, fixed Luna model in config.
  • Persistence: SQLite only for reusable extraction schemas and routing profiles (schema_store.py, default data/document_studio.sqlite3).
  • No: HTTP app API, queue, worker fleet, job store, artifact store, durable cross-session result cache, multi-user auth.

Agentic context limits

  • DocumentAgent.prepare builds compact Markdown + layout records from non-rejected elements.
  • Each context: up to ~48,000 characters and 8 pages; long documents span multiple contexts.
  • Classification uses first two pages; TOC/scalar extraction iterate contexts.
  • Chat uses full context when it fits; otherwise deterministic retrieval of up to ~40 elements + neighbors.
  • Structured text features: medium reasoning effort, one schema-invalid retry; visual recovery: high effort on original-detail crops.
  • OpenAI requests set store=False.

Result contracts

  • ParseResult: document, refined markdown, grounded base_markdown, parse JSON, elements, annotated PDF, usage, trace, metadata, recovery log.
  • Parse JSON schema version 4.4.0; full combined JSON 4.5.0.
  • Legacy extraction JSON 1.1.0; routed multi-form extraction JSON 2.0.0.
  • Markdown source spans target base_markdown, not presentation-refined Markdown.

Stack snapshot

  • Python ≥ 3.12, package version 0.5.0
  • Core deps: Streamlit, Pydantic, Pillow, PyMuPDF, OpenAI SDK, nh3
  • Local OCR extras (Linux/WSL): glmocr, torch, vLLM, transformers

6. Why this is not “just IDP”

Industry IDP usually implies an operations platform: ingestion connectors, classification taxonomies at scale, extraction models/templates, validation rules engines, human review queues, and export into ERP/CRM/RPA.

Grounded DocParse shares the document understanding middle of that story, but stops short of the platform edge:

Typical enterprise IDP piece This repo
Email / SFTP / ECM connectorsManual upload only (batch ≤ 20 files)
Multi-user review queuesSingle workstation Streamlit session
Business process automation / RPA handoffDownloads / local review only
Central model ops & fleet orchestrationLocal WSL services + optional OpenAI
Template training UI for fixed formsSchema/profile authoring, not classic template training
Schema extraction + HITLPresent (IDP-like outcome)
Form routing / packet segmentationPresent (IDP-like outcome)

So if someone asks “is it IDP?” a precise answer is: it implements IDP-like extraction/routing/review features, but its product shape and architecture are ADE-first workstation document intelligence.

7. What “ADE mode” means in this app

In the Streamlit UI, ADE mode is only a preset group for optional Luna features (Fast / Full / Custom). It is not a connection to LandingAI ADE or any external ADE product.

  • Fast: classification is the main preset-controlled Luna feature; visual recovery is a separate toggle (defaults on when key available).
  • Full: Markdown refinement + classification + TOC.
  • Custom: pick those toggles individually.
  • Extraction and chat remain on-demand, not “mode auto-run.”

Evidence: README, docs/complete-user-guide.md, docs/agentic-document-extraction-comparison.md.

8. Worked example: mixed-form business packet

Condensed from docs/how-grounded-docparse-is-agentic.md.

  1. Local OCR parses every page into grounded evidence (text, IDs, boxes, order).
  2. User loads a routing profile: categories such as new_request, update, records, plus non-extractable other.
  3. Routing agent proposes contiguous page segments with cited supporting elements.
  4. Deterministic validation checks page coverage, category names, ranges, and evidence IDs.
  5. High-confidence segments may auto-approve; low-confidence / boundary-merged segments require human review.
  6. Extraction stays blocked until every segment is approved.
  7. Only approved, extractable categories run their assigned schemas against in-memory parse subsets.
  8. Each extracted field resolves back to local-OCR-owned page/box/source text.
  9. A failed segment does not erase successful results from other eligible segments.

This orchestration — specialized goals over shared grounded state, with validation and review — is the practical definition of ADE used by this repository.
